# Отчет по лабораторной работе №5: Распределенные вычисления с использованием MPI
**Выполнил:** Круглов А. А.

## 1. Постановка задачи
Цель работы — перенос алгоритма двумерной матричной кросс-корреляции (свертки) с архитектуры с общей памятью (Shared Memory / OpenMP) на архитектуру с распределенной памятью (Distributed Memory) с использованием стандарта MPI (Message Passing Interface). Необходимо оценить накладные расходы на межпроцессное взаимодействие (IPC), сравнить работу алгоритма на локальном ПК и на реальном многоузловом суперкомпьютере, а также проанализировать масштабируемость решения.

## 2. Оборудование и программная среда
Для полноценного анализа эксперименты проводились в двух принципиально разных средах:

**Среда 1: Локальная рабочая станция**
* **Технология:** Microsoft MPI (запуск через mpiexec).
* **Модель:** Многопроцессная на одном физическом CPU (изолированные адресные пространства).
* **Среда сборки:** CMake, профиль Release (флаги оптимизации -O3, -march=native).

**Среда 2: Вычислительный кластер СГАУ «Сергей Королёв»**
* **Технология:** Intel MPI Library (модуль intel/mpi5).
* **ОС и планировщик:** Linux, система управления очередями Slurm.
* **Модель:** Распределенная на 2 физических узла (--nodes=2, --ntasks-per-node=4), обмен данными по сети.

## 3. Архитектура параллельного решения
В отличие от OpenMP, процессы в MPI не имеют доступа к общей памяти. Решение спроектировано по паттерну **Master-Worker**:
1. **Трансляция данных (Broadcast):** Процесс-мастер (Rank 0) считывает/генерирует исходные матрицы и рассылает их всем остальным процессам с помощью `MPI_Bcast`. Это оптимальнее точечной рассылки (`MPI_Scatter`), так как для вычисления свертки на границах блоков каждому процессу требуются "перекрывающиеся" строки (Halo/Ghost cells).
2. **Изолированные вычисления:** Исходная матрица логически делится на горизонтальные полосы. Каждый процесс вычисляет только свою часть результирующей матрицы. Ложное разделение кэша (False Sharing) здесь физически невозможно, так как память процессов строго изолирована на уровне ОС.
3. **Сборка результатов (Gather):** Разрозненные фрагменты собираются обратно на Master-узле с использованием `MPI_Gatherv` (сборка блоков переменного размера).

## 6. Выводы и анализ результатов
Сравнение двух сред выполнения наглядно демонстрирует фундаментальные особенности технологии MPI и выявляет классический паттерн **Communication-bound** (ограничение по пропускной способности связи).

1. **Деградация производительности на локальном ПК:**
Увеличение количества процессов на локальной машине привело к деградации производительности (для 2000x2000: 15.00 мс на 1 процессе против 20.00 мс на 8 процессах). Для эмуляции распределенной среды на одном CPU, узлу Master требуется скопировать мегабайты данных в изолированные адресные пространства других процессов через системную шину ОС (IPC), а затем собрать их обратно. Накладные расходы на копирование памяти и постоянное переключение контекста (Context Switching) полностью уничтожают выгоду от распараллеливания.

2. **Успешное масштабирование на вычислительном кластере:**
При запуске на реальном суперкомпьютере с физическим распределением на 2 узла наблюдается корректное масштабирование: время для матрицы 2000x2000 снижается с 193.89 мс до 44.89 мс (ускорение ~4.3x). Выделенные аппаратные ресурсы позволили процессам работать параллельно без жесткого разделения процессорного времени операционной системой.

3. **Анализ эффективности и сетевых издержек:**
Абсолютное время выполнения 1 процесса на кластере (193 мс) оказалось выше локального (15 мс) из-за необходимости физической пересылки данных по сетевым кабелям. Эффективность на 8 ядрах составила 54%, что объясняется:
   * **Законом Амдала:** наличием строго последовательной части кода (инициализация матриц).
   * **Network Latency:** сетевые задержки при пересылке матриц функциями `MPI_Bcast` и `MPI_Gatherv` между разными стойками серверов занимают существенную долю времени по сравнению с быстрыми математическими вычислениями $O(N^2)$.

**Общий вывод:** Технология MPI не предназначена для локального запуска быстровычисляемых алгоритмов малого объема. Свой истинный потенциал архитектура с передачей сообщений раскрывает на распределенных кластерах, однако для достижения эффективности близкой к 100%, алгоритм должен обладать высокой вычислительной сложностью (например, $O(N^3)$), чтобы время вычислений многократно перекрывало коммуникационные издержки сети.
